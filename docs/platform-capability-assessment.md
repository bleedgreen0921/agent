# Agent 平台能力现状与缺口分析

> 注：本文主体保留了工程增强实施前的评估快照；文末“工程增强落地补充”记录已经完成的对应改进，便于对照演进。

## 1. 总体判断

结合项目 README、架构说明和具体实现，当前项目已经不是普通的 RAG Demo，而是一个以“持久 Run、受控工具调用、证据化输出”为核心的 Agent 执行平台雏形。

更准确地说：

> 当前已经形成了一个可靠的、证据导向的 Agent Runtime；距离“丰富扩展的通用 Agent 平台”，主要还差平台化的能力声明、执行来源记录、统一追踪和运维恢复闭环。

| 目标 | 当前状态 | 核心缺口 |
| --- | --- | --- |
| 基础能力 | Agent 任务闭环已经完整 | 任务控制面和运行管理能力还较薄 |
| 工程可靠性 | 状态机、并发、幂等、恢复安全设计较强 | 缺少持续验证、故障修复和一致性巡检 |
| 可追溯性 | 已能追踪调用链和最终引用证据 | 尚不能完整解释或复演“为何得到这个结果” |
| 扩展能力 | 工具扩展接口较好 | 模型、执行模式、策略和证据工具协议仍较固定 |

## 2. 基础能力

### 2.1 已经实现的能力

#### 2.1.1 完整的异步任务生命周期

当前已经形成如下执行链路：

```text
提交 Run
  → 数据库排队
  → Worker 认领
  → Agent 执行
  → 模型/工具调用
  → 最终结构化生成
  → 原子发布结果
```

支持的状态包括：

- `queued`
- `running`
- `cancelling`
- `completed`
- `partial`
- `failed`
- `cancelled`

同时具备提交、按 ID 查询、取消和管理员 trace API。这意味着平台已经不依赖 HTTP 请求一直保持连接，Agent 是持久任务，而不是一次同步模型调用。

#### 2.1.2 两种 Agent 执行模式

当前支持：

- ReAct：模型自主选择工具。
- Plan-and-Execute：先生成固定计划，再逐步执行。

Plan 会被持久化为 `run_steps`，每一步记录：

- goal
- completion condition
- status
- 开始和结束时间
- 安全摘要
- error code

这使平台不仅能运行 Agent，还能表达任务是如何被分解和执行的。

#### 2.1.3 基础多租户能力

当前已经具备：

- Admin Key 与 Team Key 分离。
- 一个团队可以有多个有效 Key。
- Key 可过期、吊销。
- Run 按团队隔离。
- 文档支持 `public` 和 `restricted` ACL。
- RAG 检索在候选截断前执行 ACL。
- Agent 不接受客户端直接传入并覆盖团队 ID。

Agent 调用 RAG 时，会重新从持久 Run 中读取可信 `team_id`，而不是使用模型或调用方传入的身份信息。

#### 2.1.4 完整的 RAG 基础链路

当前已经覆盖：

- PDF、DOCX、Markdown、TXT 文档解析。
- 文档版本管理。
- 异步解析和索引。
- token 切块和 overlap。
- 来源页码、行号、标题路径。
- Dense 与 FTS 混合召回。
- RRF 融合。
- Rerank。
- 查询改写。
- 检索降级处理。
- Embedding revision 影子构建与原子切换。
- 在当前 ACL 下读取旧版本证据。

新版本只有在解析、切块和 Embedding 全部完成后才成为 active。更新失败时，旧 active 版本继续提供检索服务。

#### 2.1.5 证据化结果

最终结果不是单纯的一段文本，而是包含：

- answer
- claims
- 每条 claim 的支持类型
- claim 与 evidence 的关联
- evidence snapshot
- notices

这已经具备研究型 Agent 最核心的“结论—证据”表达能力。

### 2.2 当前缺少的能力

这里缺少的不是必须增加所有常见 Agent 功能，而是平台控制面还比较薄。

#### 2.2.1 Run 管理能力有限

目前只有提交、按 ID 查询、取消和管理员 trace，尚没有：

- Run 列表和筛选。
- 按团队、状态、时间查询。
- 安全重试或基于旧 Run 创建新 Run。
- 失败 Run 的人工处理记录。
- 排队深度和 Worker 状态查看。

这些能力比聊天界面、流式输出更符合当前平台目标，因为它们直接影响任务平台的可管理性。

#### 2.2.2 预算仍以固定调用次数为主

目前主要限制：

- 模型调用次数。
- 工具调用次数。
- 排队时间。
- 总执行墙钟时间。

但还没有：

- token 总预算。
- 成本预算。
- 单个工具预算。
- 单次调用最大耗时。
- 服务端按团队配置的预算策略。

现在的预算模型已经足够保证任务不会无限执行，但还不是完整的资源治理。

#### 2.2.3 一些常见能力尚未纳入

例如：

- 多轮会话和长期记忆。
- 人工审批节点。
- 中间进度订阅。
- 文件、表格、代码等结构化产物。
- 动态重规划。

这些是范围选择，不是当前架构缺陷。对于以异步研究任务为主的平台，未必应该立即加入。

## 3. 工程可靠性

### 3.1 已经实现的能力

工程可靠性是项目目前最成熟的方面之一。

#### 3.1.1 持久状态机，而不是内存状态

Run、步骤、模型调用、工具调用、结果和证据引用都保存在 PostgreSQL。API 和 Worker 可以独立重启，不依赖单进程内存。

#### 3.1.2 数据库租约与多 Worker 安全认领

Agent 和 RAG Worker 都使用：

- `FOR UPDATE SKIP LOCKED`
- lease token
- lease deadline
- heartbeat
- 状态条件更新

Agent 还通过 advisory lock 维护数据库级的全局并发上限。这意味着即使部署多个父 Worker，也不会突破全局并发限制或重复认领同一个任务。

#### 3.1.3 每个 Run 使用独立子进程

父 Worker 负责：

- 认领 Run。
- 维持租约。
- 检查取消和超时。
- 终止失控子进程。
- 处理子进程异常退出。

相比把多个 Agent 全部放在一个进程中，这提供了更明确的故障和资源隔离。

#### 3.1.4 保守的恢复语义

模型或工具调用遵循：

```text
持久预留预算并记录 started
  → 发起外部调用
  → 记录调用结果
  → 图 checkpoint 成功
  → 标记 checkpointed
```

当 Worker 失租时，只允许恢复所有已完成外部调用都明确进入 checkpoint 的 Run。否则终止为 `INTERRUPTED_UNKNOWN`，避免把可能已经产生副作用的调用再次执行。

这种设计不追求虚假的 exactly-once，而是明确承认外部调用结果可能未知，是可靠系统中合理的取舍。

#### 3.1.5 原子结果发布

最终结果、claims、证据快照、claim-evidence 关系和 Run 终态在一个数据库事务中发布，避免出现：

- Run 已完成但结果不存在。
- claim 引用了未保存证据。
- 部分 evidence snapshot 丢失。

数据库外键也约束了 claim 只能引用当前结果中的证据快照。

#### 3.1.6 文档更新不会破坏当前可用版本

新版本只有在解析、切块和所有相关 revision 的 Embedding 都成功后才成为 active。失败时旧版本继续服务。

这种“先准备、后切换”的方式比直接覆盖线上索引可靠得多。

#### 3.1.7 幂等和稳定错误语义

Run 提交和文档上传都支持幂等键，并区分：

- 同键同请求：重放已有结果。
- 同键不同请求：返回 409 冲突。

错误响应统一使用稳定错误码，而不是向客户端暴露内部异常。

### 3.2 当前缺少的能力

#### 3.2.1 缺少持续执行的完整集成验证

测试设计已经覆盖：

- 并发槽位。
- checkpoint 恢复安全。
- 预算。
- ACL。
- 文档版本。
- 降级。
- 双 Agent 模式。
- 工具错误分类。
- 历史证据快照。

但当前没有 CI 配置。在未配置隔离 PostgreSQL 的环境中，大部分数据库状态机和 Agent 集成测试会被跳过。

所以现状是：可靠性机制存在，也有对应测试，但没有自动、持续地证明这些机制始终成立。这是工程可靠性最值得优先补强的地方之一，而且几乎不增加运行时复杂度。

#### 3.2.2 缺少故障修复闭环

当前系统擅长安全地识别失败，但失败之后的操作能力不足：

- 没有受控 requeue。
- 没有基于旧 Run 创建重试 Run 的正式语义。
- 没有孤儿文件清理。
- 没有数据库与文件目录一致性巡检。
- 没有 stuck job 检查命令。
- 没有 checkpoint 与业务调用记录的一致性检查工具。

也就是说，当前已经解决了“不要错误恢复”，但还没有完全解决“确认失败之后，管理员应该如何安全处理”。

#### 3.2.3 文件系统与数据库不是统一事务

上传流程已经尽量补偿文件删除，但进程如果在文件移动完成、数据库事务提交前崩溃，仍可能产生孤儿文件。

这不要求立即引入对象存储或分布式事务。增加一个只读扫描和安全清理命令，就能在较低复杂度下补齐。

#### 3.2.4 配置错误通常在运行时暴露

模型 URL、模型名、工具 provider、服务 token、数据库权限等配置，很多要等到具体 Run 执行时才会发现问题。

当前缺少轻量的启动前检查，例如：

- 配置格式是否有效。
- provider 是否可加载。
- 工具名是否冲突。
- checkpoint 表是否存在。
- 运行角色权限是否符合预期。
- lease、heartbeat 和 deadline 参数是否合理。

这类 fail-fast 校验很适合当前项目，不需要引入复杂的服务发现体系。

#### 3.2.5 部分数据库不变量只存在于代码中

Run 状态有数据库 CHECK，但 `model_calls`、`tool_calls`、`run_steps` 的部分状态约束主要由代码保证。随着扩展增加，非法状态更容易被新代码写入。

可以逐步把真正稳定的不变量放入数据库，但没有必要给所有字段一次性堆叠大量约束。

## 4. 可追溯能力

### 4.1 已经实现的能力

#### 4.1.1 跨服务关联链已经建立

当前可以形成如下关联：

```text
team_id
  → run_id
    → step_id
      → model_call_id
        → tool_call_id
          → RAG request_id / retrieval_id
            → evidence_id
              → claim
                → evidence snapshot
```

RAG 审计记录：

- run ID
- tool call ID
- team ID
- index revision
- 请求状态
- 降级信息

Agent 工具调用记录：

- service request ID
- retrieval ID
- evidence IDs
- 触发该工具的 model call ID

这已经不是普通文本日志，而是一条结构化业务调用链。

#### 4.1.2 调用 trace 具备隐私控制意识

模型 trace 默认只保存：

- 消息数量。
- 结构化输出 schema。
- token 数。
- 输出类型摘要。
- 异常类型。

工具参数只保存：

- 参数名称。
- 完整参数的 SHA-256。

这避免了为了追踪而把所有用户问题、工具参数和结果重复写入业务 trace。

#### 4.1.3 最终引用有强结构约束

发布时会检查：

- `support=evidence` 的 claim 必须引用证据。
- 引用的 evidence 必须确实由本 Run 获得。
- citation 集合必须与所有 claim 的引用完全一致。
- 不允许重复或凭空声明 citation。

#### 4.1.4 证据快照保证历史解释能力

最终引用的正文、标题、文档版本和来源定位被复制到 Agent schema。

因此，源文档后续即使发生以下变化，历史报告仍然可以展示当时实际引用的证据：

- 上传新版本。
- 修改 ACL。
- 逻辑删除。
- 重新构建索引。

#### 4.1.5 索引 revision 已进入检索审计

RAG 检索记录 active embedding revision，说明项目已经考虑到相同查询在不同索引版本下可能得到不同结果。

### 4.2 当前缺少的能力

当前可追溯性已经完成了第一层“能关联”，但第二层“能解释”和第三层“能复演”还不完整。

#### 4.2.1 缺少 Run 级执行清单

`agent_runs` 有固定的 `graph_version='v1'`，但没有完整记录本次执行实际使用的：

- 代码版本或 Git commit。
- prompt 版本。
- Agent graph 版本。
- 模型 provider 和精确模型 revision。
- temperature 等关键模型参数。
- 启用的工具 provider 集合及版本。
- 服务端预算策略。
- 最终使用的 RAG index revision。

因此可以知道调用了哪个模型名，却不能精确回答“这次执行是在什么完整配置下产生的”。

一个追加式 `execution_manifest` 会比引入复杂全链路系统更契合当前目标。

#### 4.2.2 检索过程不可完整复演

RAG audit 当前记录请求身份、状态和 revision，但没有记录：

- query 摘要。
- 改写后 query 摘要。
- Dense 候选 ID 与距离。
- FTS 候选 ID 与分数。
- RRF 结果。
- Rerank 顺序。
- 最终 evidence ID 列表。

Agent 侧只保存最终 evidence IDs。

因此能够证明某个工具调用返回了这些证据，但无法解释某个证据为什么排在另一个证据前面。

不一定需要保存查询全文和所有分数。保存查询哈希、最终候选 ID 和顺序，已经能显著增强解释能力。

#### 4.2.3 最终答案与 claims 的关系仍依赖模型自觉

程序验证了引用 ID 合法，却没有验证：

- answer 中的重要陈述是否都进入 claims。
- claim 是否真的被对应 evidence 支持。
- answer 是否与 claims 冲突。
- `unverified` claim 是否被答案表达为确定事实。

此外，当前结构允许 claims 为空。

这意味着现在实现的是“引用完整性校验”，还不是“语义支持性校验”。

#### 4.2.4 Agent 与 RAG 的 trace 尚未统一展示

数据层已经可以通过 run/tool call ID 关联，但管理员 trace API 目前只读取 Agent schema。

调查一次完整执行，需要分别查询：

- Agent run、step、model 和 tool trace。
- RAG retrieval audit。
- 最终 claims 和 snapshots。

这里未必需要新观测系统。一个只读的 trace 聚合接口或诊断命令，就能解决大部分问题。

#### 4.2.5 管理操作没有审计事件

以下行为会影响未来的执行或检索结果，但没有独立审计事件：

- ACL 修改。
- 文档逻辑删除。
- 团队创建。
- Key 签发、过期、吊销。
- Embedding revision 切换。

数据中通常能看到最终状态，却不一定能回答谁在什么时候把它从什么改成了什么。

#### 4.2.6 trace 不是防篡改审计

运行角色对所属 schema 有普通 DML 权限，因此理论上可以修改或删除 trace。

对于个人研究项目，这并不意味着需要立即实现不可篡改账本。但概念上应明确：

- 当前是可查询的业务追踪。
- 当前不是合规级不可篡改审计。

## 5. 扩展能力

### 5.1 已经实现的能力

#### 5.1.1 Agent 核心已经和 RAG 解耦

`agent_service.execution` 不直接依赖具体 RAG 实现，而是通过 `module:factory` 形式的工具 provider 加载工具。

默认 provider 是：

```text
agent_service.tools.rag:tools
```

新的非 RAG 工具不需要修改 Agent 图执行器，这一点已经有测试覆盖。

#### 5.1.2 横切能力由中间件统一处理

所有工具自动获得：

- 持久 Run 上下文。
- team ID。
- key ID。
- step ID。
- 调用预算。
- 调用 trace。
- 触发模型调用 ID。
- 统一错误分类。

因此，扩展工具不需要各自重新实现预算、身份和 trace。

#### 5.1.3 工具错误有统一语义分类

当前已经区分：

- `RecoverableToolError`：作为错误观察返回 Agent。
- `FatalToolError`：终止 Run。
- 未分类异常：记录 `TOOL_CALL_FAILED`。

这为新增工具提供了统一的错误模型。

#### 5.1.4 RAG 是独立服务契约

Agent 只通过 HTTP/JSON 调用 RAG，不访问 RAG schema。将来可以：

- 替换 RAG 实现。
- 单独扩展 RAG。
- 接入其他证据服务。
- 将 Agent 与 RAG 分别部署。

#### 5.1.5 Evidence 契约支持多证据来源

只要新工具把满足公共 `Evidence` 契约的数据放入 `context.evidence`，最终发布逻辑就能复用现有的 claim、citation 和 snapshot 机制。

这个方向是正确的：证据能力不必永久绑定于当前 RAG。

### 5.2 当前缺少的能力

#### 5.2.1 工具扩展目前是 Python 插件，还不是完整 provider 协议

Provider 目前只返回一组 `BaseTool`，尚不能声明：

- provider 名称和版本。
- 工具能力说明。
- 是否产生证据。
- 是否有外部副作用。
- 是否允许自动重试。
- 是否要求幂等键。
- 默认超时。
- 成本类型。
- 所需配置。
- 健康状态。

尤其是“是否有副作用、是否可安全重试”，会直接影响现有恢复设计。

当前不需要一次性设计复杂插件系统，但当接入第二、第三类真实工具时，这些元数据会逐渐成为必要条件。

#### 5.2.2 证据工具仍然依赖约定

普通工具和证据工具在类型层面没有区别。证据 provider 必须手工操作 `runtime.context.evidence`，并确保数据满足公共契约。

这适合当前阶段。但随着证据来源增加，可以逐步形成一个小型、明确的 evidence result 协议，而不是继续依赖文档约定和共享可变字典。

#### 5.2.3 执行模式扩展并不开放

虽然工具是可插拔的，但 Agent 编排仍是硬编码的：

- API `mode` 只有两个 Literal。
- 数据库有 mode CHECK。
- `execute_run` 使用 if/else。
- Plan 状态结构写在 `execution.py`。

因此新增以下模式时，需要同时修改契约、数据库和执行器：

- supervisor
- reflection
- map-reduce research
- human approval
- specialized workflow

也就是说，目前是工具扩展性较强，而不是编排扩展性较强。

#### 5.2.4 模型层是单一全局配置

当前模型固定通过 `ChatOpenAI` 和全局环境变量创建，尚不支持：

- 不同 Run 使用不同的服务端模型策略。
- planner、final 和 tool-agent 使用不同模型。
- 模型 fallback。
- 模型能力声明，例如是否支持工具调用、结构化输出。
- 模型版本和配置快照。

不一定需要允许客户端选择模型，但服务端应逐渐具备模型策略层，否则以后接入不同模型会持续侵入执行代码。

#### 5.2.5 工具策略是部署级全局配置

`AGENT_TOOL_PROVIDERS` 决定整个 Worker 加载什么工具。当前没有：

- 按团队的工具 allowlist。
- 按任务类型选择工具集。
- 按执行模式选择工具策略。
- 工具级预算。
- 工具权限策略。

目前这种方式足够简单和安全。只有当工具数量真正增加后，才值得增加服务端策略层。

#### 5.2.6 扩展兼容性缺少持久记录

如果 provider 代码或工具 schema 更新，历史 Run trace 只记录工具名，不记录 provider、provider version 或 schema revision。

这同时影响扩展性和可追溯性：系统可以扩展，但历史记录无法精确说明当时运行的是哪个版本的工具。

---

## 6. 核心结论

这个项目目前最强的不是功能数量，而是以下三点：

1. 把 Agent 当作持久、受预算约束、有明确终态的任务执行系统。
2. 对外部调用恢复采取保守而正确的处理方式。
3. 把最终答案拆成 claim，并保存实际引用的证据快照。

当前最主要的不足也不是少了某个流行功能，而是：

- 可靠性机制还没有形成自动持续验证和故障处理闭环。
- 追踪链能够关联，但还缺少完整执行来源和检索决策信息。
- 工具已经可插拔，但模型、编排和策略仍然固定。
- 平台能执行任务，但管理员对大量 Run 的管理能力还比较有限。

---

## 7. 渐进增强优先级

如果严格遵循“小步、低复杂度、不破坏现有语义”的原则，建议采用以下顺序。

### 7.1 让 PostgreSQL 集成测试进入持续执行流程

首先保证已有可靠性设计不会随着后续修改而回退。这项工作主要增加验证能力，几乎不增加运行时复杂度。

### 7.2 增加 Run 级 execution manifest

以追加字段或独立表的方式，记录：

- graph version
- prompt version
- model identity 和关键参数
- provider 列表及版本
- 预算策略
- 代码版本摘要

它是可追溯性和扩展兼容性的共同基础。

### 7.3 增加只读的一致性检查与恢复辅助命令

优先检查而不是自动修复：

- stuck Run 和 processing job。
- 过期租约。
- checkpoint 与业务调用记录关系。
- 数据库记录与本地文件关系。
- 未引用或孤立的持久化记录。

确认规则稳定后，再增加范围明确的修复操作。

### 7.4 补充统一 trace 聚合视图

把 Run、步骤、模型、工具、RAG retrieval、claim 和 evidence snapshot 串成一条只读时间线，不必立即引入新的可观测性基础设施。

### 7.5 在接入第二类真实外部工具时补充 provider 元数据协议

重点声明：

- provider 和工具版本。
- 是否有外部副作用。
- 是否支持安全重试。
- 幂等性要求。
- 超时策略。
- 是否产生可引用证据。

避免在没有真实扩展需求时提前设计庞大的插件系统。

### 7.6 在出现真实需求后再抽象编排和模型策略

只有出现第三种执行模式或多模型实际需求时，再把固定的 if/else 和全局模型配置抽象为注册表或策略层。

---

## 8. 当前不需要优先引入的复杂度

以下能力在更大规模或更严格场景中可能有价值，但不是现阶段实现项目目标的关键缺口：

- Kubernetes。
- 独立消息队列。
- 完整 OpenTelemetry 平台。
- 复杂 PostgreSQL RLS。
- 不可篡改审计账本。
- 大规模插件市场。
- 流式聊天 UI。
- 通用长期记忆框架。

当前更重要的是把已有的正确设计变成可持续验证、可解释、可诊断和可安全演进的能力，而不是通过堆叠基础设施增加表面上的平台复杂度。
